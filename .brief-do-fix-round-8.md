## B1 (P0) — your own B2 fix 500s every workspace over 100 notes

`listFilesPage` and `listAssetsPage` now measure a page's byte cost from a metadata query, then
**re-fetch the page rows** with:

```sql
SELECT * FROM files WHERE rowid IN (?,?,?, … ) ORDER BY updatedAt ASC, path ASC
```

One bound parameter per row. **Cloudflare DO SQLite caps bound parameters at 100.** The page is
bounded by *bytes* and never by *row count*, so any workspace of ordinary small notes overflows
it instantly.

Reproduced through real HTTP against real workerd (`SELF.fetch`), files of 11 bytes each:

| files | `GET /api/files` |
|---|---|
| 95, 96, 97, 98, 100 | 200 |
| **101, 110, 128, 200, 500, 1000, 2000** | **500 `{"error":"Internal error."}`** |

```
Error: too many SQL variables at offset 236: SQLITE_ERROR
    at listFilesPage (worker/durableObject/files.ts:129)
uncaught exception; source = Uncaught (in promise)
```

`GET /api/assets` fails identically at 200 assets. **`runOrphanAssetCleanup` also throws
`too many SQL variables` on a 300-note workspace** — so the cron could not be re-armed even
after B2 below is fixed.

This is worse than the bug B2 was assigned to fix: the client calls `getFiles` on every run, and
a real workspace here is ~1,778 files. Every pull would 500. Total sync outage.

`git show HEAD:apps/www/worker/durableObject/files.ts` has no `rowid IN` — this pattern is new
this round.

### Required
Page rows without an unbounded parameter list. Prefer a **single** query that both measures and
returns (the byte columns can be selected alongside `*`), or keyset pagination on
`(updatedAt, path)` with a hard row cap. Whatever you choose, the page must be bounded by BOTH
bytes and row count.

**Proof required**: through the real route, `GET /api/files` and `GET /api/assets` return 200 and
the complete correct set at 1, 99, 100, 101, 500, 2000, and 5000 rows — content and order intact
across pages, no duplicates, no misses. Same for `runOrphanAssetCleanup` at 300+ notes. Then
temp-break your fix and confirm the 500 returns.

**Add a row-count regression test to the shipped suite.** Its absence is why this shipped: no
existing test exercises more than 20 rows in one page.

## B2 (P0) — GC deletes a referenced image, fifth axis: NFD + percent-encoding

Stored NFD `images/café.png`; a live note references the percent-encoded NFC form
`images/caf%C3%A9.png` — exactly what a browser-derived `img.src` produces. Real upload → real
`POST /api/files` → real `runOrphanAssetCleanup` across the grace period: `rowsDeleted: 1`, R2
object gone. Same data-loss class as the previous four axes; the tombstone propagates to the
desktop and deletes the user's local original.

Cause: in `assetSearchStrings` each form is **percent-encoded first and NFC-normalised after**.
Percent escapes are ASCII, so `normalize("NFC")` can no longer reach the encoded bytes — NFD
encodes to `cafe%CC%81`, the note holds `caf%C3%A9`, neither variant matches.

Each half works alone (NFD + raw NFC reference survives — your own test; ASCII + percent-encoding
survives). Only the combination fails.

### Required
Emit **both NFC and NFD spellings before encoding**, so every normalisation form has its own
encoded variant. Keep the fail-safe direction: over-retaining is correct, deleting a referenced
asset is not.

**Proof required**: real upload → real route → real cron. All four combinations survive —
{NFD stored, NFC stored} x {raw reference, percent-encoded reference} — plus everything round 7
already proved (nested `note.assets/`, `./` and `../` climbs, case differences, partially
encoded, every syntax, legacy rows). A genuinely unreferenced asset must **still be collected**.

## Smaller items

**M1 — the page budget ignores JSON escaping.** The budget counts UTF-8 bytes of the stored
value, but the response is JSON: a control character costs 6 bytes (``), `"` and `\` cost
2. Twelve notes of 2MiB of U+0001 paged fine (all 200) but produced a **37,749,170-byte wire
response** — above the 32MiB the budget is sized against. No 500 (the RPC hop counts raw bytes),
so this is not a blocker, but charge escape expansion in the per-row cost or cap rows per page
so the claim "no response approaches the ceiling" is actually true.

**L1 — `listAssetsForGcPage` charges `row.hash.length`** (UTF-16 units) while every other budget
uses `utf8ByteLength`. Harmless for hex hashes, but it is the exact character-vs-byte
inconsistency this work exists to remove. Make it consistent.

**L2 — the brief's M4 attribution was wrong, no action needed.** `batchVersion.test.ts`'s
*"errorResponse wires typed errors…"* calls `errorResponse` directly and stays green when the
router stops calling it. The wiring **is** covered — by *"a malformed asset path segment reaching
the router is a generic 500"*, which goes red. Coverage exists; do not add more.

## The rule for this round
> **A page bounded by one dimension is unbounded in every other.** B1 exists because a byte
> budget replaced a row budget and nothing capped rows. When you bound a result set, enumerate
> every limit the underlying engine imposes — bytes, rows, bound parameters, statement size —
> and bound against all of them.
