# BLOCKER 1 (P0) — the asset GC deletes referenced images, and the deletion reaches the user's disk

**The nightly cron is currently DISARMED in `wrangler.toml`** (I commented out the
`[triggers]` block before deploying, precisely because of this). It stays disarmed until this
is fixed and reviewed. Do not re-enable it — that is my call, not yours.

## The bug
`referencedAssetPaths` / `isAssetPath` in `apps/www/worker/orphanAssets.ts` only counts a
markdown image reference when some path segment ends in **`.assets`**. But `POST /api/assets`
accepts **any** path, and the desktop asset walker
(`packages/workspace-scan/src/walkers/assetsWalker.ts`) uploads **every** image anywhere in
the workspace.

So an image at `images/logo.png`, referenced by a live note, is marked orphaned → tombstoned
after the 7-day grace → **deleted from R2**. The tombstone then reaches the desktop as
`remote.deleted`, `packages/sync/src/sync.ts` routes it to `assetOps.toDelete`, and the
executor calls `fs.deleteFile(...)` — **deleting the user's local original.**

Reproduced end-to-end against real workerd driving the real `runOrphanAssetCleanup`:
```
note.md: "![logo](images/logo.png)"      (live, references it)
after 2 cron cycles: asset row deleted=true, R2 download = 404
```
The user's real workspace has **11 image references outside `.assets` folders**.

## This is the same class as the bug that took three rounds to kill
Round 4 unified *structural normalisation* across writer, deleter and GC — correctly. But the
**reachability predicate** still derives a different notion of "is this path an asset" than
the writer accepts. Same shape: **two code paths disagreeing about what a path means.**

## The rule
> **The GC's notion of "referenced" must be derived from the same facts as the writer's notion
> of "storable". If the writer accepts a path, the matcher must be able to match it. One
> function answers "does this markdown reference resolve to this stored asset", and its answer
> must not depend on folder naming.**

## Required
1. A markdown reference resolves to a stored asset by **path equality after the shared
   structural normalisation**, regardless of what any folder is called. Drop the `.assets`
   segment requirement from the reachability test. Keep `.assets` if it is used elsewhere for
   *placement* — just stop letting it decide *reachability*.
2. **Fix the encoding gap in the same pass.** `decodeURI` refuses to decode reserved
   characters, so an asset whose filename contains `#` or `?` never matches and is deleted.
   Confirmed survival matrix: space/`%20`, `+`, `&`, `=`, `,`, `@`, `%25`, combining accents
   all survive; **percent-encoded `#`, angle-bracket `#`, and percent-encoded `?` are
   deleted**. Handle reserved characters and the `<...>` angle-bracket link form (currently
   truncated by `split("#")`).
3. **Un-mark already-marked rows.** The cron ran in production on 2026-09-02 and 2026-09-03,
   so real assets are already flagged. A now-correctly-referenced asset must have its mark
   cleared on the next scan, not merely avoid a new mark. Test that a marked-then-referenced
   asset is restored to unmarked.
4. Prove it by driving the **real** `runOrphanAssetCleanup` across the grace period, with
   assets uploaded through the **real** `POST /api/assets` route. Round 3 shipped a
   regression test that passed while its bug was live because it hand-built rows instead of
   posting — do not repeat that.
5. Cover at minimum: `images/logo.png`, a bare `logo.png` at the workspace root, a nested
   `docs/img/a.png`, filenames containing `#` and `?`, and a genuinely unreferenced asset
   which **must still be collected** (do not "fix" this by disabling the GC).

# BLOCKER 2 (P0) — one oversized note jams the entire workspace sync, permanently

## The bug
The real ceiling is Durable Object SQLite's per-value limit (`SQLITE_TOOBIG`), not the
declared caps. Measured on real workerd:

| content bytes | result |
|---|---|
| 2,100,000 | `200 {"ok":true}` |
| 3,145,728 | `500 {"error":"Internal error."}` + unhandled rejection |
| 3MiB via `/api/files/batch` | `500 code:UNKNOWN` |

`MAX_PUSH_FILE_BYTES` / `MAX_PUSH_BATCH_BYTES` are 8MiB and `MAX_REQUEST_BYTES` is 16MiB —
all **4x above the real limit**, so nothing catches the 2–8MiB band.

Two aggravating factors:
- In `pushFile` (`workspaceDurableObject.ts`), `upsertFile(...)` sits **outside** the `try`,
  so the SQLite throw escapes the DO's error mapping entirely and surfaces as an opaque 500
  plus an unhandled rejection.
- **Client side:** a non-2xx becomes a thrown `CloudflareResponseError`
  (`packages/cloudflare-client/src/httpClient.ts`), and sync's push loop in
  `packages/sync/src/sync.ts` — `for (const op of computed.toPush) { await pushLocal(...) }`
  — has **no try/catch**. One oversized note aborts `execute()` before sync state is written,
  so **the whole workspace stops syncing on every subsequent run, forever**, until that note
  is deleted. The user sees only "Internal error."

This is the likeliest defect to actually bite: the product is for agent-generated Markdown,
and a pasted log crosses 2MB easily.

## Required
1. **Server:** determine the real per-value limit empirically and set the per-file cap safely
   below it. Return a typed, clean **413** naming the file and the limit. Move `upsertFile`
   inside the `try` so nothing escapes the DO's error mapping. Same treatment on the batch
   path. No unhandled rejection under any input.
2. **Client:** one file's failure must not abort the sync run. Catch per-file push failures,
   record them, **continue the loop**, and still write sync state so progress is durable.
   Surface the failed files to the caller so the UI can report them.
3. Distinguish **permanent** failures (413 — this file will never fit; do not retry it every
   run) from **transient** ones (5xx, network — retry next run). A permanently-rejected file
   must not silently vanish: it stays local, unsynced, and reported.
4. Prove with a test that a workspace containing one oversized note **still syncs every other
   file**, writes state, and reports the failure — and that the next run also succeeds.
