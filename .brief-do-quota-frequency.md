# Brief — stop the Durable Object row-read burn (frequency, not page size)

(`hubble-source`). Report honestly; do not claim numbers you did not observe.

## What is wrong

Rounds 2-8 (see `.brief-do-fix-round-*.md`) all bounded **how many rows a single
listing reads**. That work is done — do not reopen it. This round is a different
failure: **how OFTEN listings happen**.

The loop, verified:

1. `packages/sync/src/sync.ts:722-750` pushes **one HTTP request per file**,
   serially (`pushLocal` at `:698-714` → `backend.pushFile`).
2. Every `pushFile` bumps the workspace version and broadcasts to every socket
   (`apps/www/worker/durableObject/workspaceDurableObject.ts:191-192`).
3. Every broadcast makes every client re-list the whole workspace. Desktop does
   it with **zero debounce** (`apps/desktop/electron/cloudSyncWiring.ts:1202-1212`);
   web does it with no debounce and no in-flight guard
   (`apps/www/src/shell/AppShell.tsx:150`).
4. **A client cannot recognise its own echo.** The payload is `{type, version}`
   with no origin (`apps/www/worker/durableObject/broadcast.ts:14-24`), so the
   device that just wrote re-reads everything in response to its own write.
5. Each sync run lists the workspace **twice** (`sync.ts:149-151` and
   `sync.ts:771-773`), and each listing reads ~2x the rows it returns (metadata
   scan + keyset range re-fetch, `apps/www/worker/durableObject/files.ts:100-192`).

A 50-file burst costs roughly 140,000 row reads on the Mac alone, plus ~70,000
per open browser tab. Free tier is 5,000,000/day.

## Scope — four fixes, ALL CLIENT-SIDE. Do not modify the worker or the DO.

### 2a. Batch the pushes

The server endpoint is **already built, tested and deployed, with zero callers**:
`POST /api/files/batch` → `handlePushFilesBatch`
(`apps/www/worker/routes/files.ts:244-349`) → `pushFilesBatch`
(`workspaceDurableObject.ts:294-370`). It bumps the version and broadcasts
**exactly once per batch** (`:358-366`).

Wire the client to it:

- `packages/sync/src/backend.ts` — add `pushFilesBatch` to the `SyncBackend`
  interface, next to the existing `pushFile` (`:8-24`).
- `packages/cloudflare-client/src/backend.ts` — implement it against
  `POST /api/files/batch`. Request body: `{workspaceId, files:[{path,
  contentHash, content, deviceId}]}`. Success response is `{ok:true, version}`;
  failure is `{error, code}`. Reuse the existing request/validation helpers in
  that file rather than inventing new ones.
- `packages/sync/src/sync.ts:722-750` — replace the per-file loop.

Server caps you MUST respect (chunk against all of them):
`MAX_PUSH_BATCH_FILES = 100`, `MAX_PUSH_BATCH_BYTES = 8MiB`,
`MAX_PUSH_FILE_BYTES = 2MiB` per entry
(`workspaceDurableObject.ts:55, 62, 74`). An empty array is a 400 — never send one.

**Behaviour you must not regress.** Today one bad file never aborts a run: it is
classified by `isPermanentFailure` into `nextRejected` / `result.failedFiles` and
the loop continues (`sync.ts:722-750`). A batch is all-or-nothing server-side.
Therefore:

- A file over the 2MiB per-entry cap must NOT go in a batch — push it singly so
  its existing permanent-rejection (HTTP 413) handling still fires per file.
- If a batch request fails, **fall back to pushing that chunk file-by-file** so
  one poisoned file cannot take 99 good ones down with it, and so the existing
  per-file error classification still runs. Do not swallow the batch error.
- `result.pushed`, `failedFiles`, `rejectedFiles` and the progress `tick()` must
  end up exactly as they would have before, per file.

Apply the same treatment to the sidecar push loop (`sync.ts:556-592`) ONLY if it
falls out cleanly; if it complicates the change, leave it and say so.

### 2b. Suppress self-echo — WITHOUT a server change

Every mutation response already carries the new version number, and the client
throws it away: `MutationOkResponseSchema` is `{ok:true, version:number}`
(`packages/cloudflare-client/src/schemas.ts:46-49`) but
`backend.ts:93-100` does `await requestJson(...)` without capturing it.

Implement **exact** self-echo suppression:

- Capture the returned `version` from `pushFile`, the new `pushFilesBatch`, and
  the delete calls.
- Record those version numbers in a small bounded ledger (a `Set` plus a FIFO
  cap of, say, the last 200 — do not let it grow forever).
- In `packages/cloudflare-client/src/subscriber.ts:223-238`, skip `notifyAll()`
  when the incoming version **is a member of that ledger**.

Match on exact membership, NOT on "version <= my latest". A `<=` rule would
silently swallow another device's change that landed with a lower number, which
is a data-loss-shaped bug. Exact membership cannot do that.

Wiring: create one shared ledger object where the backend and subscriber are
constructed together, and pass it to both — desktop
`apps/desktop/electron/cloudSyncWiring.ts:294-303`, web
`apps/www/src/shell/AppShell.tsx:94-97`. Prefer this over threading a device id
through the whole sync engine. If a shared object is genuinely awkward at one of
the two call sites, say so in your report rather than forcing it.

### 2c. Debounce the notification-driven resync

- Desktop: `cloudSyncWiring.ts:1202-1212` schedules with delay `0`. Give it a
  real debounce (400ms is a reasonable default; keep it well under
  `MAX_DEBOUNCE_WAIT_MS = 5000`). Note the comment there claims "a remote push is
  already one discrete event" — 2a is what finally makes that true. Update the
  comment to match reality.
- Web: `AppShell.tsx:150-186` has no debounce and **no in-flight guard**. Add
  both, so overlapping refreshes cannot stack.
