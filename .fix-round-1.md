## 1. HIGHEST — pending-hold race for a folder that arrives WHILE syncing

`cloudSyncWiring.ts:725` (`onDirEvent`) fires the ordinary sync debounce (`onFsEvent()`, 250ms, capped by a 5000ms max-wait in `scheduleSync`) on every `addDir`, and only then (re)schedules a **pure, uncapped 2000ms** `pendingCheckTimer` for `detectAndHoldPendingFolders`.

A folder materializing continuously for more than 5 seconds — exactly what an agent worktree checkout does — keeps resetting the 2s pending check, while the 5s sync max-wait has no such reset and fires anyway. The new folder's files can be synced BEFORE the pending-hold ever catches them.

This is the headline use case: "a worktree folder appears, hold it pending." The only existing test (`cloudSyncWiring.largeWorkspace.test.ts`) covers a large folder that already existed before enabling — not live arrival.

**Required:** a targeted test with real timers reproducing a folder arriving over >5 seconds while sync is active, proving its files are NOT pushed before the hold applies. Then fix. Likely shape: a newly-seen directory makes its whole subtree provisionally ineligible for sync until the pending check has run once, rather than racing two independent timers.

## 2. Review dialog — three of its four advertised behaviours are untrue

Meanwhile `getCloudSyncPreview` (`cloudSyncWiring.ts:1173`) is fully wired through `main.ts:1462` and `preload.ts:52`, uses the real `planSync`, and populates the real `SyncFolderSummary.autoExcluded` field — and **nothing calls it. It is dead code.**

- **Reasons are invented.** `CloudSyncReviewDialog.tsx:181-188` guesses ("starts with `.`" → "hidden folder default") instead of reading `autoExcluded` (`"gitignored" | "nested-repo" | "over-threshold"`).

- **No scan count-up.** `getLocalSyncScopePreview` takes an `onScan` callback that `main.ts:1477-1483` never forwards, and `ipcMain.handle` is request/response so there is no progress channel at all. Large workspace = a static "Scanning workspace…". The Settings progress bar IS honest — match it here.

**Required:** use the engine-backed preview, emit real reasons from the engine (never guessed in the UI), include excluded folders as greyed re-includable rows, and give the dialog real scan progress. Add a test file for this component — it currently has none, and it is the highest-risk new code.

## 3. Pre-enable count can undercount vs. what actually syncs

`getLocalSyncScopePreview` (`cloudSyncWiring.ts:1077`) is a **third independent walker**. It never calls `notesWalker`/`discoverWorkspaceFiles` and never reads `.gitignore`/`.ignore` — only the flat exclusion list. The real sync path does honor nested `.gitignore` with negation.

Reproduced: a workspace with `.gitignore` containing `build/`, plus `build/generated.md` and `top.md` → preview reports **2 files**, actual sync syncs **1**.

Its own comment at line 1073 claims the number shown before enabling is the number that actually happens. Make that true: one walker, not three. Add a test that gives the preview a workspace WITH a `.gitignore` — no current test does, which is why this was invisible.

## 4. Status reports "idle" while a write burst's tail is unsynced

`cloudSyncWiring.ts:481-533`. At `MAX_DRAIN_ITERATIONS = 3`, a 4th reentrant trigger does `handle.pending = 0; break;` — it zeroes the "something changed again" counter and exits WITHOUT the pass that counter was supposed to guarantee. The adjacent comment says triggers are "never dropped"; at the cap boundary that is false.

Not permanent data loss (the next event or restart catches it), but the app says **idle** as if fully synced, and if the burst simply stops (a big `git checkout`, a rebase) those files sit un-pushed and invisible. `MAX_DRAIN_ITERATIONS` appears in zero test files.

**Required:** when the cap is hit, do NOT report `idle` — keep the changed-signal and surface an honest status (still-pending work), and schedule a follow-up pass. Test the cap boundary.

## 5. Worktree protection still rests on a blunt folder name

Protection is entirely the `.claude` entry in `DEFAULT_CLOUD_SYNC_EXCLUDED_DIR_NAMES`. That is the hotfix, not the design (decision **D-LW1** in the architecture note). Still missing:

- `.git/info/exclude` and git's global `core.excludesFile` are never read — `IGNORE_CONFIG_FILES` in `packages/workspace-scan/src/file-discovery.ts` is only `[".gitignore", ".ignore"]`. **This is the original root cause**: git ignored `.claude/worktrees` via `.git/info/exclude`, mdly could not see it, and walked in.
- **Nested-repo detection**: a directory containing its own `.git` is a repo/worktree boundary and is essentially never workspace content. Auto-exclude with reason `"nested-repo"` (the enum value already exists). This is what should protect worktrees — not a hardcoded name.

Blunt `.claude` exclusion also drops legitimate notes (there were 42 markdown files in `.claude/briefs`). Once 5 is done, reconsider whether `.claude` still belongs in the default list.

## 7. Minor

- **Leading slash is inverted from gitignore.** `scope.ts:32` and `file-discovery.ts:171-174` strip a leading `/` then match as a bare any-depth name. In gitignore, leading `/` means root-anchored — the opposite. `normalizeExcludedEntries` (`scope.ts:50-65`) strips it on save too, so typing `/node_modules` silently means "anywhere". Either honor gitignore's meaning (preferred — your docstring invokes it) or stop invoking gitignore and document the difference in the exclusions UI.
- **Duplicated matching logic.** `scope.ts:22` `matchesExcludedPattern` and `file-discovery.ts:164` `isExcludedByEntries` are hand-copies, byte-identical today, nothing keeping them so. The comment admits it. Make one the single source (shared low-level module) — fixing #7's leading-slash bug in one place only is exactly the drift this causes.
- **Dead code:** `scope.ts:112` — `statSync(...).isDirectory() || true` is always `true`; the call is a no-op. Decide whether a `.git` file (worktree gitlink) and a `.git` directory should both count (they should) and write that plainly.
- **Double-wired progress.** `SettingsDialog.tsx` subscribes to progress over BOTH `onCloudSyncStatusChange`'s embedded payload AND `onCloudSyncProgressChange`. Pick one.
