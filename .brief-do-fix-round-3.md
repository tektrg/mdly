## 1. P0 — YOU INTRODUCED A DATA-LOSS REGRESSION IN THE ASSET GARBAGE COLLECTOR

Moving `normalizeWorkspacePath` into `worker/paths.ts` you also **changed its behaviour**
(per-segment `.trim()`, and `null` on a whitespace-only segment). That function is not only
a write-path helper — `referencedAssetPaths` uses it to decide which R2 objects are still
referenced, and `cron.ts` **deletes** everything it reports as an orphan.

Reproduced:

```
stored asset : "note.assets/ shot.png"
markdown ref : ![shot](note.assets/%20shot.png)
refs found   : ["note.assets/shot.png"]    <- trimmed, no longer matches
orphans      : ["note.assets/ shot.png"]   <- eligible for DELETION
```

An asset under a directory named `" "` normalizes to `null`, so its reference disappears
entirely. Both matched correctly before your change. The grace period does not save them —
a still-referenced asset is a candidate on every scan. Leading/trailing spaces in filenames
are legal on macOS and Linux.

**Fix:** restore `normalizeWorkspacePath` to its ORIGINAL semantics (no trim, no
whitespace-segment rejection) and keep it as the GC matcher. Put the trimming and the
stricter rejection in `canonicalFilePath` ONLY, which is the write path. Two functions, two
jobs. Add a test that a referenced asset whose path has a leading/trailing space is NOT
reported as an orphan.

## 5. P1 — Control and zero-width characters bypass the invariant and are stored

Confirmed stored with 200: a path ending in a NUL character (`U+0000`), a path ending in a
zero-width space (`U+200B`), and a 5,000-character path segment (no length cap).

`.trim()` strips Unicode whitespace but not NUL or ZWSP. These don't clobber the canonical
log, but Node's `fs` throws `ERR_INVALID_ARG_VALUE` on a path containing NUL — one poisoned
row breaks the desktop client's write loop on **every subsequent sync**.

**Fix:** in `canonicalFilePath`, reject control characters (U+0000 through U+001F, and
U+007F) and zero-width/bidi characters, and cap total path length (1024 is fine). Return 400
on violation.

## 6. P1 — Existing non-canonical rows become unreachable after this deploy

The site is LIVE with real data. Any row already stored as `./x.md`, with a trailing space,
or under a `../` path becomes undeletable once `deleteFile` canonicalizes, and turns into a
permanent duplicate when the client re-pushes the canonical spelling. No migration ships.

**Fix (low risk, do this rather than a migration):** in `deleteFile`, if no row matches the
canonical path, fall back to deleting the raw path as sent. Keeps legacy rows removable
without a rewrite. Test both spellings.
