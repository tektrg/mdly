# Fix BUG-LW1 — Durable Objects free-tier row-read blowout (quadratic storage-cap scan)

**Server side only.** Another agent is concurrently editing `packages/sync/` and `apps/desktop/` in this same checkout. **Do not touch either.** Your scope is `apps/www/worker/` and nothing else.

## The bug

Production error on `garden.theindie.app`: *"Exceeded allowed rows read in Durable Objects free tier"* (limit: 5,000,000 rows read/day).

Cause — a full table scan on **every single file push**:

```
pushFile()                              worker/durableObject/workspaceDurableObject.ts:125
  └─ assertWithinStorageCap()           worker/durableObject/workspaceDurableObject.ts:222
       └─ approximateWorkspaceBytes()   worker/durableObject/schema.ts:77
            └─ SELECT SUM(LENGTH(content)) FROM files WHERE deleted = 0
```

`SUM(LENGTH(content))` cannot use an index — it scans every row. And the client pushes **one HTTP request per file** (sequential `await` in a `for` loop in `packages/sync/src/sync.ts:103`), so pushing N files scans a table growing 0 → N:

**rows read = N(N−1)/2**

Real case: a 1,778-file workspace = **~1.58 million rows in one first sync**. Three app relaunches ≈ the entire daily budget. Cost is quadratic in file count: 5,000 notes ≈ 12.5M rows per sync.

## Task 1 (REQUIRED — this alone fixes the reported error)

Replace the scan with a **running byte total** so the cap check is O(1) instead of O(rows).

- The `meta` table already exists and already holds exactly this shape of counter (`version`, `schema.ts:60`, with `bumpVersion`/`currentVersion` at `schema.ts:63-74`). Add a `bytes` key the same way.
- Adjust the total incrementally on insert / update / soft-delete / undelete / hard-delete, for **files and assets both** if assets contribute to the cap (check — `approximateWorkspaceBytes` currently only sums `files`; preserve whatever the current semantics are, do not silently change what counts).
- An **update** needs the OLD content length to adjust the total. Use SQLite `RETURNING`, or read the single row by primary key first — either is O(1) per push. Do NOT reintroduce a scan.
- **Migration matters:** existing deployed workspaces have rows but no `bytes` counter. On first access after deploy, compute the total once (one scan, unavoidable and acceptable) and persist it. Make this idempotent and safe to run on an empty DO.
- Keep `approximateWorkspaceBytes`'s external behaviour identical — same number, same cap semantics, same `StorageCapExceededError`. Only the cost changes.

Expected result: pushing N files goes from ~N²/2 rows read to ~N.

## Task 3 — cheap change-check endpoint

The client currently calls `GET /api/files?since=...` on every sync cycle, which reads every row changed since that timestamp — including the rows it just wrote itself. A version counter already exists (`currentVersion`, `schema.ts:63`) and is already broadcast (`broadcast.ts:19`).

Expose a **1-row** endpoint returning the current version, so a client can skip the file listing entirely when nothing has changed. Server side only — do not wire the client.
